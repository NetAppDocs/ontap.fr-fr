= Récupérer après des opérations de basculement automatiques non planifiées du cluster ONTAP
:hardbreaks:
:allow-uri-read: 
:nofooter: 
:icons: font
:linkattrs: 
:imagesdir: ../media/


[role="lead"]
Une opération de basculement automatique non planifié (AUFO) se produit lorsque le cluster principal est hors service ou isolé. SnapMirror active sync détecte de telles pannes et initie un basculement automatique non planifié vers le cluster secondaire. Le cluster secondaire est converti en cluster principal (le cluster privilégié) et commence à servir les clients. Notez que la détection des pannes et le traitement du basculement ne peuvent être effectués qu’avec l’assistance de l’ONTAP Mediator.


NOTE: Après un basculement automatique non planifié, il est important de réanalyser les chemins d'accès de l'hôte afin d'éviter toute perte de chemins d'E/S.



[[reestablish-the-protection-relationship-after-an-unplanned-failover]]
== Rétablir la relation de protection après un basculement non planifié

Une fois le cluster principal d'origine, par exemple Cluster A, rétabli, SnapMirror active sync rétablit automatiquement la protection dans le sens inverse. Si vous souhaitez restaurer l'état initial, en faisant de Cluster A le cluster principal préféré, vous pouvez effectuer un basculement manuel en lançant une opération de basculement planifiée à l'aide de System Manager ou de l'interface de ligne de commande ONTAP.

[role="tabbed-block"]
====
.System Manager
--
.Étapes

IMPORTANT: D'ONTAP 9.8 à ONTAP 9.14.1, la synchronisation active SnapMirror est appelée SnapMirror Business Continuity (SM-BC).

. Accédez à *Protection > Relations* et attendez que l'état de la relation indique « InSync ».
. Pour effectuer un retour en arrière et reprendre les opérations sur le cluster source d'origine, cliquez image:icon_kabob.gif["Icône des options de menu"] et sélectionnez *Basculement*.


--
.CLI
--
Vous pouvez surveiller l'état du basculement automatique non planifié à l'aide du `snapmirror failover show` commande.

Par exemple :

....
ClusterB::> snapmirror failover show -instance
Start Time: 9/23/2020 22:03:29
         Source Path: vs1:/cg/scg3
    Destination Path: vs3:/cg/dcg3
     Failover Status: completed
        Error Reason:
            End Time: 9/23/2020 22:03:30
Primary Data Cluster: cluster-2
Last Progress Update: -
       Failover Type: unplanned
  Error Reason codes: -
....
Vous pouvez surveiller l'état de la relation de protection inverse à l'aide de la commande  `snapmirror show` sur le cluster principal d'origine.

Par exemple :

....
ClusterA::> snapmirror show
                                                                               Progress
Source             Destination  Mirror        Relationship   Total             Last
Path         Type  Path         State         Status         Progress  Healthy Updated
-----------  ----  ------------ -------       -------------- --------- ------- --------
vs3:/cg/dcg3 XDP   vs1:/cg/scg3 Snapmirrored  InSync          -         true    -
....
Vous pouvez effectuer un retour au cluster principal d'origine à l'aide de la commande  `snapmirror failover start`.

Par exemple :

....
ClusterA::> snapmirror failover start -destination-path vs1:/cg/scg3
....
Reportez-vous à la link:https://docs.netapp.com/us-en/ontap-ems-9131/smbc-aufo-events.html["Référence EMS"^] pour en savoir plus sur les messages d'événement et sur les actions correctives à mener.

--
====


[[resume-protection-in-a-fan-out-configuration-after-failover]]
== Reprise de la protection dans une configuration « Fan-Out » après le basculement

À partir d'ONTAP 9.15.1, SnapMirror active sync prend en charge la reconfiguration automatique de la branche de distribution après un basculement dans une relation SAN. Dans une configuration NAS, vous devez reconfigurer manuellement la relation de protection après un basculement de SnapMirror active sync. La branche de distribution asynchrone peut être une relation de groupe de cohérence ou une relation de volume indépendante. Pour plus d'informations, consultez link:interoperability-reference.html#fan-out-configurations["configurations « fan-out »"].

Si vous utilisez ONTAP 9.14.1 ou une version antérieure et que vous rencontrez un basculement sur le cluster secondaire dans la relation de synchronisation active SnapMirror, la destination asynchrone SnapMirror devient défectueuse. Vous devez restaurer manuellement la protection en supprimant et en recréant la relation avec le terminal asynchrone SnapMirror.

.Étapes
. Vérifiez que le basculement s'est terminé correctement :
`snapmirror failover show`
. Sur le point de terminaison asynchrone SnapMirror, supprimez le point de terminaison « Fan-Out » :
`snapmirror delete -destination-path _destination_path_`
. Sur le troisième site, créez des relations asynchrones SnapMirror entre le nouveau volume primaire de synchronisation active SnapMirror et le volume de destination asynchrone « Fan-Out » :
`snapmirror create -source-path _source_path_ -destination-path _destination_path_ -policy MirrorAllSnapshots -schedule _schedule_`
. Resynchroniser la relation :
`snapmirror resync -destination-path _destination_path_`
. Vérifiez l'état et l'état de la relation :
`snapmirror show`
